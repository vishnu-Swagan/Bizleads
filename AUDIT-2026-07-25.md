# BizLeads — Gap Audit vs. Master Prompt

**Date:** 2026-07-25
**Scope:** Static read of `app/backend` (15,590 LOC Python) and `app/frontend/src` (12,837 LOC TS/TSX) against `uploads/paste-text.txt` (master prompt) and its 26 acceptance criteria.
**Method:** Code reading only. Nothing was executed, built, deployed, or modified. No database, no running server, no browser.

---

## Verdict

`\.atoms/PROGRESS.md` marks Phase A and Phase B complete. **Neither is complete.** What exists is a well-styled Phase-A *shell*: the routes, the score-breakdown UI, the pricing page and the credit counter are all there and look right. Underneath, the multi-tenant model, the billing lifecycle, the async job system, the evidence layer and the provider discipline are absent or bypassable.

**Acceptance criteria: 3 pass, 4 partial, 19 fail.** (Table at the end.)

Three findings are severe enough to block any public deployment, in this order:

1. **Six API routers are completely unauthenticated**, including `workspaces` and `credit_ledger`. Anyone on the internet can grant themselves an Agency plan with unlimited credits, or read every lead in the database with contact details.
2. **There is no Stripe webhook.** Subscriptions are activated once by a client-triggered call and never updated again. Cancel in Stripe → the account keeps access forever. The same endpoint can be replayed to reset credit usage to zero on demand.
3. **The app invents businesses.** When the geo provider is unconfigured *or simply returns no rows*, discovery silently falls back to an LLM that fabricates business names, addresses, phone numbers and email addresses, and returns them in the same result list as real data. The master prompt forbids this explicitly (§14, criterion 6).

## 1. Critical — security and tenancy

### 1.1 Six routers have no authentication at all
`workspaces`, `workspace_members`, `credit_ledger`, `provider_connections`, `offer_profiles`, `search_jobs` expose full CRUD (`GET / POST / PUT / DELETE`, plus `/batch` and `/all`) with **no `get_current_user` dependency and no ownership filter**. Verified by inspecting every route signature in `backend/routers/`.

Directly exploitable, no account needed:

| Call | Effect |
|---|---|
| `PUT /api/v1/entities/workspaces/{id}` with `{"plan":"agency","monthly_credits":999999,"subscription_status":"active"}` | Free unlimited plan — on your workspace or anyone else's |
| `GET /api/v1/entities/workspaces` | Every customer's plan, Stripe customer ID and subscription ID |
| `POST /api/v1/entities/credit_ledger` | Mint ledger entries |
| `DELETE /api/v1/entities/workspaces/{id}` | Destroy any workspace |
| `GET /api/v1/entities/provider_connections` | Every workspace's `config_json` (provider settings; any key stored there leaks) |
| `POST /api/v1/entities/workspace_members` | Add yourself to any workspace |

`backend/routers/credit_ledger.py:31` onward and `backend/routers/workspaces.py` are the clearest examples — compare against `backend/routers/leads.py:124`, which does inject `current_user`.

### 1.2 `/all` endpoints dump the whole database unauthenticated
`GET /api/v1/entities/leads/all` (`backend/routers/leads.py:159`), `/lead_notes/all`, `/ai_interaction_logs/all` — no auth, no user filter, `limit` up to 2000. Leads carry `contact_email` and `contact_phone`. This is a personal-data breach of every customer's prospect list, and it fails criteria 1 and 5 on its own. The docstring says "without user limitation," so it is deliberate scaffolding that was never removed.

### 1.3 CORS is wide open with credentials
`backend/main.py:92` — `allow_origin_regex=r".*"` together with `allow_credentials=True`, all methods, all headers. Any web page a logged-in user visits can call the API as them. This turns every gap above into a one-click attack.

### 1.4 AI endpoints are unauthenticated cost exposure
`POST /api/v1/aihub/gentxt|genimg|genvideo|genaudio|transcribe|analyzepdf` require no auth. Anyone can run your model budget to zero.

### 1.5 Tenancy is per-*user*, not per-*workspace*
`models/leads.py` has `user_id` and **no `workspace_id`**. Same for `lead_notes`. The master prompt (§15) requires `workspace_id` on every tenant-owned row. Consequences beyond security: a Pro workspace's 3 seats each see only their own leads — there is no shared pipeline, so seats, roles (Owner/Admin/Member/Viewer), invitations and assignment cannot work as specified. Roles are not modelled anywhere; `dependencies/auth.py:59` has only a global `admin` flag.

## 2. Critical — billing integrity

### 2.1 No webhook endpoint exists
Zero matches for `webhook`, `construct_event`, or `STRIPE_WEBHOOK` across the backend. Criterion 3 fails completely, and with it the entire subscription lifecycle: renewals, cancellations, failed payments, downgrades, and reactivation are all invisible to the app. **A customer who cancels in Stripe retains full access indefinitely.**

### 2.2 `verify-payment` is forgeable and replayable
`backend/routers/payments.py:268`:
- It accepts any `session_id` and **never checks `session.metadata.user_id == current_user.id`** — so a session ID belonging to someone else activates *your* workspace.
- It checks `session.status == "complete"` but not `payment_status`.
- It is not idempotent, and every successful call sets `workspace.credits_used = 0` (line 307). Buy Solo once, then call `verify-payment` with the same session ID whenever you run out of credits — unlimited credits, forever.

### 2.3 Trials never expire
`trial_ends_at` is written in three places and **read in none**. No expiry check, no read-only state after entitlement loss.

### 2.4 The credit ledger is decorative
The `credit_ledger` table has `idempotency_key` and `balance_after` columns, and `payments.py` imports the model — but nothing ever writes to it. Credits are a plain mutable integer on `workspaces`. There is no immutable ledger, no replay safety, no reservation/finalization, and no reconciliation. Criterion 4's "replay-safe credit ledger" fails.

### 2.5 The "deep" pass charges 3× for identical work
`routers/discover.py:121` sets `credit_cost = 3` for `pass_type="deep"`. `audit_website` is imported at line 21 and **never called**. The deep pass runs exactly the same code path as the quick pass. Users are billed triple for nothing. There is no two-pass architecture (§8).

### 2.6 Missing billing surface
No customer portal, no cancel, no proration preview, no invoices, no coupons, no top-up endpoint (`CreditTopUpRequest` is defined at `payments.py:59` with no route), no grace period. Prices are inline `price_data` (`payments.py:210`), not env-configured Stripe Price IDs — §1 requires plans, prices and entitlements to be admin/env configurable, and the `PLANS` dict is hardcoded at `payments.py:35`. `max_seats` is stored and never enforced.

## 3. Critical — data honesty

### 3.1 Fabricated businesses are returned as live results
`routers/discover.py:160-183`: if MapBox is not configured **or returns zero results**, it falls through to `discover_businesses()` → `services/business_search.py:78`, which prompts an LLM to "Identify {limit} REAL, specific local businesses… Phone numbers must use the correct country code… Email domains should be realistic." The model invents plausible names, streets, phones and emails. These are returned in the same array, with scores attached, savable as leads, and emailable.

The master prompt is unambiguous (§14): *"Never silently return fabricated businesses as live results."* Criterion 6 fails. The practical harm is that a paying user cold-emails addresses that belong to nobody, or to the wrong business.

### 3.2 The one honesty signal in the UI is wrong in both directions
`pages/app/Discover.tsx:372` renders `Source: {dataSource === 'google_places' ? 'Google Places API' : 'AI Discovery'}`. The backend only ever returns `'mapbox'` or `'ai'` (`discover.py:158,174`), so **real MapBox results are labelled "AI Discovery"** and the `google_places` branch is unreachable. A small grey line saying "AI Discovery" is also not the "Integration Setup state / disabled paid action" that §14 requires.

### 3.3 Google Places is dead code, and the docs claim otherwise
`services/google_places.py` is imported by **no router or service**. MapBox POI/geocoding is what's wired (`services/mapbox_places.py`). Both `.wiki.md` and `PROGRESS.md` state "Connect Google Places API for accurate business data (with AI fallback)" — that line is false. It also matters technically: MapBox POI search returns no email, no review velocity, no website quality, so those fields have no real source at all.

### 3.4 Mock leads auto-seed into the database on startup
`main.py:72` calls `initialize_mock_data()` in the lifespan, which inserts `backend/mock_data/leads.json` — 8 fabricated leads ("Mario's Pizzeria", Rome; `user_id: "1466317"`) — whenever the leads table is empty. Unlabelled, indistinguishable from real records. Suppressed only if `MGX_IGNORE_INIT_DATA` is set in the environment. Criterion 26 fails by default.

### 3.5 Unknown is still encoded as zero
`leads.website_score` defaults to `0` (`models/leads.py:17`). In `services/scoring.py`, `get_website_state()` maps score 0 → `"unknown"` (line 56), while `build_score_breakdown()` simultaneously treats score < 20 as *"Very weak website presence"* and assigns `need = 80` (line 80). **The same record is "unknown" and "very weak" at once.** Criterion 9 and §2's explicit prohibition both fail.

## 4. High — the product core is display-deep

### 4.1 Four of the six scores are constants
`services/scoring.py:94-126`: `buyability` defaults to 50, `timing` to 30, `confidence` to 45, and `agency_fit` is **hardcoded to 50** at lines 133 and 148. Only Need and Reachability are computed, and their inputs (`website_score`, `social_score`, `contact_email`) come from the AI path in the fallback case. The Service Lens (§2) does not exist — there is no per-subscriber recalculation of Fit. Weights are hardcoded at line 155, not versioned or configurable. The breakdown UI is real and well-built; the numbers behind it are not evidence-derived.

### 4.2 Scores are never persisted
`pages/app/Discover.tsx:172` saves only `website_score` and `social_score`. The `leads` table has no columns for need / buyability / timing / reachability / agency_fit / confidence / priority / score_version / risk / evidence. **The moment a business is saved as a lead, its entire scoring evaporates.** Leads, Pipeline and Analytics therefore show no scores, and "Why this score?" cannot be answered for any saved lead — which is the product's whole premise.

### 4.3 Discovery results are never stored
No canonical business table, no source records, no evidence ledger. Results exist only in one HTTP response. Consequences: no deduplication (criterion 8 fails — nothing in the codebase attempts it), no "exclude existing leads" filter, no saved searches, no monitoring, no freshness tracking, and re-running an identical search charges credits again.

### 4.4 "Job-based async" is synchronous
`POST /discover/run` creates a `Search_jobs` row, runs the provider call inline, and marks it `complete` in the same request (`discover.py:136-209`). `progress_pct` goes 10 → 100. There is no queue, no worker, no polling, no partial results, no cancel, no retry. The browser blocks for the full duration. Criterion 7 fails.

### 4.5 Suspected runtime bug in the discovery path
`discover.py:153` calls `await db.rollback()` immediately after `commit()` to "close transaction before slow external call." Line 217 then reads `workspace.monthly_credits` and `workspace.credits_used` from that now-expired ORM instance. Under async SQLAlchemy, a lazy refresh outside a greenlet context typically raises `MissingGreenlet`. **Not verified by execution** — worth reproducing before touching anything else, because if it fires, every successful search 500s after the credits have already been deducted.

## 5. High — asserted-but-absent features

### 5.1 The Automations page is a brochure
`pages/app/Automations.tsx` is 122 lines with **zero API calls**. "No active automation queues" and "No automation activity yet" are hardcoded strings. It displays a green `Draft-Only Mode` badge and the line *"Emergency stop available · Suppression lists enforced · Draft-only by default"* (line 53) — that string is the **only** occurrence of "suppress" anywhere in the repository. None of it exists.

Worse, the backend that *does* exist is ungated: `routers/outreach.py` `POST /send-email` and `POST /send-bulk` will send real mail with no suppression check, no eligibility check, no approval record, no lawful-basis record and no unsubscribe mechanism. Criteria 16 and 17 fail — the guardrails are UI copy, not code. The older working AI-automation UI (`pages/Automation.tsx`, backed by `routers/automation.py`) is orphaned; the Phase-A rewrite replaced a functioning feature with a description of one.

### 5.2 Entire feature areas have zero references in the codebase
Grepped across `backend/routers`, `backend/services`, `backend/models`, `frontend/src`:

Proof Rooms · Revenue Gap Twin · owner claim / verification / disputes / opt-out · project briefs · lead reservations · saturation hashes · admin console · audit log · saved-search monitoring · email verification · password reset · notifications · tasks & reminders · outcomes & score calibration · competitor benchmarks · screenshots

That is Phases **C, D and E in full**, plus parts of A and F.

### 5.3 Public site and routes
Present: `/`, `/pricing`. §12 specifies roughly fifteen routes. Absent: `/product`, `/how-it-works`, `/use-cases/*`, `/faq`, `/contact`, `/login`, `/signup`, `/forgot-password`, `/verify-email`, `/claim/[token]`, and **all three legal pages** (`/legal/terms`, `/legal/privacy`, `/legal/acceptable-use`). No legal pages is a launch blocker independent of code quality — you cannot take subscription payments or process prospect data without them.

Under `/app`, missing per §19: `searches/[id]`, `twins`, `proof-rooms`, `briefs`, `campaigns`, `notifications`, `/admin/*`, and the settings split — Settings has only Workspace and Billing tabs, versus the specified profile / workspace / offer / team / integrations / billing / usage. Lead detail has 4 tabs (Overview, Evidence, Contacts, Notes) against the 8 in §9.

### 5.4 Exports are unrestricted
`pages/app/Leads.tsx:79` builds the CSV client-side from already-fetched rows. No plan gating, no server call, no logging, no suppression or licence filtering. Criterion 20 fails.

### 5.5 No tests
Zero test files in the repository. Phase F (security tests, tenant-isolation tests, billing/webhook tests, accessibility QA, provider-failure tests) has not started.

## 6. What actually works

Worth protecting during any rework:

- **Auth plumbing is sound.** OIDC with PKCE, JWKS fetch, real RS256 signature verification with issuer and audience checks (`core/auth.py:126`). User IDs are hashed in logs. No secrets in client code — the frontend has no hardcoded keys and reads only `VITE_*` public config.
- **Frontend route gating works.** All eight `/app` pages wrap in `AppShell`, which blocks render on `!user` and offers sign-in (`components/AppShell.tsx:63`). (This is UI-level only — it is not what makes §1.1/§1.2 exploitable.)
- **Pipeline drag-and-drop persists.** `handleDrop` calls `leads.update` and survives refresh — criterion 12's core assertion passes.
- **The 100%-conversion complaint is fixed.** `pages/app/Analytics.tsx:46-47` computes lead-to-win and closed-deal win rate separately, and line 92 renders "{won} of {total} total leads". The closed-deal tile is missing its denominator line, but the specific misleading metric called out in §11 is gone.
- **The score-breakdown UI, "Why this score?" drawer, credit estimation screen, and website-state badges are built and look right.** They need real inputs, not a rewrite.
- **SSRF risk is low by accident:** audits are delegated to Google's PageSpeed API rather than fetched server-side, so the app does not fetch arbitrary prospect URLs itself. There is no URL validation or private-range blocking (criterion 24 is unimplemented), but there is currently no server-side fetch path to exploit. Adding screenshots or crawling changes that immediately.

## 8. Prioritized plan

### Stop-the-bleeding (do before this touches a public URL — roughly a day)
1. Add `get_current_user` to every route in `workspaces`, `workspace_members`, `credit_ledger`, `provider_connections`, `offer_profiles`, `search_jobs`; add ownership filters to each service call.
2. Delete every `/all` endpoint, or gate behind `get_admin_user`.
3. Replace the CORS regex with an explicit origin allowlist.
4. Gate the `aihub` endpoints behind auth.
5. In `verify-payment`, require `session.metadata["user_id"] == current_user.id`, check `payment_status`, and make it idempotent — never reset `credits_used` on a repeat call.
6. Set `MGX_IGNORE_INIT_DATA` in every non-local environment, or drop `initialize_mock_data()` from the lifespan.
7. Stop the AI fabrication fallback: when the provider is unconfigured or returns nothing, return the Integration Setup / empty state. Keep the AI path only behind an explicit, separate, labelled Demo workspace.

None of this is architectural. It is roughly a day, and it converts the project from "publicly exploitable" to "incomplete."

### Foundation (real Phase A — 1–2 weeks)
8. Add `workspace_id` to `leads` and `lead_notes` with a migration and backfill; make workspace resolution a dependency, not a per-route `select`.
9. Build the Stripe webhook: signature verification, idempotent event log, subscription lifecycle → workspace state.
10. Move credits onto the immutable ledger with reserve/finalize/refund and a real `idempotency_key`; make `workspaces.credits_used` a derived view of it.
11. Enforce `trial_ends_at`, `max_seats`, and plan entitlements in a single server-side `require_entitlement` dependency.
12. Legal pages, `/login`, `/signup`, email verification, password reset.
13. Fix the deep pass: either call `audit_website` or stop charging 3 credits.
14. Reproduce and fix the `discover.py:153` rollback bug.

### Make the product real (real Phase B — 2–3 weeks)
15. Persist discovery results: canonical business table with provider provenance (provider, external ID, retrieved-at, confidence, licence class), then dedup on top of it.
16. Persist scores and breakdowns on the lead, with `score_version` and per-field source and timestamp.
17. Separate unknown from zero throughout — nullable score columns, explicit `unknown` state, and UI that renders "not checked" rather than 0.
18. Make discovery genuinely async: job queue, polling endpoint, partial results, cancel, credit reconciliation on failure.
19. Wire PageSpeed into a real deep pass, feeding real Need and Confidence inputs instead of the current constants.

### Then, and only then
Phases C (Twin, Proof Rooms), D (Exchange, claims), E (outreach with real suppression and approval records), F (tests, a11y, launch checklist). Roughly two-thirds of the master prompt is still ahead of you — the current build is the front third, and its foundation needs the work above before anything is stacked on it.

### One strategic note
The master prompt's differentiator is the evidence-to-revenue loop: real measured evidence → Proof Room → outcome → calibration. Right now the evidence layer is an LLM's imagination and none of it is stored. Every downstream phase — Twin, Proof Room, calibration, Expected Agency Value — depends on §4.3 and §4.2 (persisted, sourced, timestamped evidence) existing first. If you build Proof Rooms before that, they will be citing fabricated facts to real business owners under your customers' branding. Item 15 is the true critical path, not item 20.
